# Three.js path

The runner copies the pinned Vite + Three.js scaffold into two isolated workspaces and installs its locked dependencies before either model starts. Each model may change `index.html`, `src/main.js`, and `src/style.css`; at least `index.html` or `src/main.js` must change. This keeps dependencies and the build tool fixed while allowing source prompts that require a single HTML implementation.

Prompt manifests may declare `requirements.singleHtml`, `requirements.webgl2Required`, and `requirements.localThreeCdnMapping`. A single-HTML entry must put its application HTML, CSS, and JavaScript in `index.html`, without changing or referencing the scaffold's separate source files. WebGL2-required prompts receive an explicit rendered-context check. For a prompt that explicitly names a Three.js CDN, recognized ESM URLs from jsDelivr, unpkg, or esm.sh are fulfilled from the pinned local `three` package during verification and recording. This is dependency normalization, not a CDN benchmark; every other external request remains blocked.

Verification checks scaffold integrity, runs the production build, serves it on localhost, opens it in headless Chromium, rejects page/console errors, requires a visible canvas within the shared policy startup timeout, and measures rendered pixel diversity. Chromium probes hardware WebGL first and uses SwiftShader only when that probe fails; the selected renderer and startup timeout are reused for both participants.

A successful entry is reopened at a native 1200×676 viewport and recorded through Playwright's low-overhead native pipeline, patched from its upstream 25 fps / 1 Mbps defaults to 30 fps / 8 Mbps for this pinned Skill dependency. The source WebM is trimmed to the exact interaction interval and transcoded to a high-quality H.264 intermediate. Participants are recorded serially to avoid GPU/CPU contention. The runner performs the same continuous, time-scheduled 30 Hz pointer path for both participants while the page renders at its natural frame rate. Each recording is checked for dimensions, duration, final frame count, interaction timing, and clean bounded shutdown before A-above-B X composition. The adjacent `.mkv.json` file keeps `captureMode`, renderer, browser-frame cadence, recorder settings, interaction time, close status, and probe evidence local.

If either participant exhausts all severe-cadence retries, the real-time measurements remain evidence of the work's actual local performance. The final comparison is then recaptured for both participants with one shared deterministic pipeline: a virtual `requestAnimationFrame` / `performance.now` / `Date.now` clock advances by exactly 1/30 second, the same pointer path advances once per output frame, and a native 1200×676 PNG is captured after every rendered frame. FFmpeg encodes exactly 360 frames into each 12-second intermediate. Slow rendering can increase wall-clock capture time but cannot drop output frames. The metadata records both the original real-time result and deterministic frame-render wall time. This is capture normalization, not a performance correction: it does not edit model code, reduce resolution, rerun the model, or claim that the scene achieved real-time 30 fps. Browser timers and network timing remain real, so prompt fixtures should keep animation on `requestAnimationFrame` as the pinned Three.js scaffold does.

Remote models must not add dependencies or remote assets. Static source checks reject non-mapped remote URLs, fetch, XMLHttpRequest, and WebSocket use, while the browser blocks every non-local request that is not an enabled Three.js CDN mapping. A build or browser error is eligible for an equal repair round. Dependency-install, browser-launch, or local-server failures are infrastructure failures and abort publishing.
