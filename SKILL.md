# Visual Code Model Benchmark

Run a reproducible local comparison and return one self-describing MP4 optimized for posting to X. Model A is on top, model B is below, both recordings fill the frame without the legacy web layout or empty letterboxing, and the final composition includes the pinned local benchmark soundtrack. Model inference may use provider services, but code generation, validation, recording, composition, and upload orchestration stay on the user's machine.

Each model profile declares a **runner**, the CLI agent harness that executes it: `codex` (OpenAI Codex CLI; ChatGPT login or any OpenAI-compatible endpoint) or `claude` (Anthropic Claude Code CLI; Claude login or any Anthropic-compatible endpoint). The same skill works whether it is invoked from Codex or from Claude Code; only the participants' runners differ.

## Workflow

Treat the directory containing this `SKILL.md` as `SKILL_DIR`. Invoke every benchmark command as `npm --prefix SKILL_DIR run benchmark -- ...`; this applies the pinned high-quality Playwright recorder settings before launching the command and does not depend on the user's current working directory.

1. Run `npm --prefix SKILL_DIR run benchmark -- list-models` to discover the display-name-to-profile-ID mapping and each profile's runner. Copy IDs from this output; do not infer them from display names. Do not expose secret values.
2. Ask the user to choose model A, model B, then `threejs` or `twigl`, then one prompt listed by `npm --prefix SKILL_DIR run benchmark -- list-prompts --method <method>`. The list reports whether the prompt has one or multiple creative rounds. When the two profiles use different runners, tell the user the comparison is "model + harness" (see Fairness below) before they confirm.
3. Run `npm --prefix SKILL_DIR run benchmark -- describe --model-a <a> --model-b <b> --method <method> --prompt <prompt-id> [--publish]`. Show its resolved model/profile IDs, runner per participant, `harness.crossRunner`, reasoning presets, every ordered creative-round prompt and hash, generation soft/hard/idle limits, repair limit, recording duration, publishing choice, and `confirmationToken` to the user. Obtain one confirmation before paid model calls and publishing unless the user's current request already explicitly authorizes both. Omit `--publish` unless publishing is explicitly authorized.
4. Run `npm --prefix SKILL_DIR run benchmark -- doctor --models <a>,<b>` before the first real run or after configuration changes. This is a static/local check and does not send a model prompt. Add `--probe-models` only when the user explicitly wants the optional paid few-token availability probe. Warnings (for example a non-empty `~/.claude/CLAUDE.md`) remain separate from failures.
5. Run `npm --prefix SKILL_DIR run benchmark -- run --model-a <a> --model-b <b> --method <method> --prompt <prompt-id> --confirmed-plan <confirmationToken> [--publish]`. Use exactly the same reasoning and publish options used for `describe`; a changed plan invalidates the token. The run performs a low-effort, few-token preflight call per Claude-runner participant before generation and aborts the other participant immediately if one fails. Creative generation and repair use the fixed profile quality level: `max` for every bundled Flash profile and `high` for every other bundled profile. Never downgrade them automatically.
6. While a model is running, summarize the 60-second progress records from `model-<side>/logs/progress.jsonl`: elapsed time, idle time, soft-limit warning, estimated thinking tokens when available, tool calls, and file writes. The 3600-second soft limit warns only; the 10800-second hard limit or 900 seconds without runner output terminates the phase.
7. Report the final MP4, each participant's runner, completed creative-round count, generation/verification status, repair count, runner-reported token usage, and the published page URL when present. For every participant, always expose two explicit metric outputs: `completeTaskTime` and `listPriceEstimatedCost`. `completeTaskTime` is exactly the sum of all creative-round durations and repair-round durations; it excludes preflight, dependency installation, validation, recording, composition, and publishing. `listPriceEstimatedCost` is actual reported creative/repair token usage multiplied by the lowest checked public API list price configured for each token category. When the same category has multiple tariffs (for example peak/off-peak, promotional/standard, standard/fast, or 5-minute/1-hour cache write), use the lower tariff; do not incorrectly price uncached tokens as cached tokens. A time-limited lower tariff must carry a review deadline, after which the estimate becomes unavailable until refreshed. This is a lower-price estimate, never the account's settled charge. If usage or a verified applicable price is unavailable, keep the output item but set its status to `unavailable` and state why. Do not present an infrastructure failure as a model failure.

After a verification or recording policy change, or after a recording infrastructure failure, `npm run rerecord -- <absolute-run-directory>` may revalidate and rerecord both existing workspaces without another model call. Treat an output made from already repaired workspaces as a preview of those exact workspaces rather than a fresh clean benchmark. It writes `comparison-x.mp4` by default and must not be used to swap workspaces or cherry-pick only one participant.

If exactly one participant failed for an infrastructure reason after the other completed every creative round, first run `npm --prefix SKILL_DIR run benchmark -- describe-retry --run <source-run-id-or-path> --side <a|b>`, show the recovery plan and obtain its new confirmation token, then run `npm --prefix SKILL_DIR run benchmark -- retry-participant --run <source-run-id-or-path> --side <a|b> --confirmed-plan <token>`. The failed side restarts from the clean template with the exact source-run prompt bytes; the completed side's allowed output files and recorded metrics are reused. The new report is labeled `recovered-single-participant`. Never start this paid retry automatically.

The final handoff also identifies the soundtrack title and license.

## Fairness

- Same runner for both profiles (`harness.crossRunner = false`): the harness is identical, so differences are attributable to the models and their providers. This is the cleanest comparison.
- Different runners (`harness.crossRunner = true`): Codex CLI and Claude Code have different system prompts, tools, and editing strategies. The video then compares each model inside its own CLI ("model + harness"). Always disclose this in the report and in any caption; never present it as a pure model comparison.
- One open-source model may exist as two profiles (for example `deepseek-v4-pro` on `codex` and `deepseek-v4-pro-claude` on `claude`); pick the runner that matches the other participant when a same-harness comparison is wanted.

## Invariants

- Send the same ordered normalized prompt-round bytes to both agents and give them identical templates, workspace instructions, time limits, repair limits, browser settings, and recording settings. Template workspaces contain `AGENTS.md` and `CLAUDE.md` as byte-identical copies so each runner's native instruction discovery sees the same rules.
- Keep every active prompt source-attributed. Preserve public source wording by default; when the user explicitly requests a fairness adaptation, retain the verbatim original and exact transformation in manifest provenance and send the same adapted bytes to both participants.
- Use one pinned Three.js scaffold. Models may edit `index.html`, `src/main.js`, and `src/style.css`, with at least the HTML entry or main module changed. Per-prompt requirements can enforce a single-HTML source layout, require WebGL2, or map explicitly requested Three.js module CDN URLs to the pinned local package. This mapping is not a CDN score and never permits unrelated external requests.
- Resolve one WebGL rendering profile for the benchmark process. Prefer available hardware WebGL, fall back to SwiftShader only when the WebGL probe fails, and use the resolved profile for both participants.
- Record participants serially so two WebGL scenes and video encoders do not compete for the same GPU/CPU. Drive the configured pointer interaction against wall-clock progress at the capture frame rate and skip stale pointer samples when the browser falls behind; never replay an accumulated input backlog. Record ordinary cadence-boundary misses as visible warnings. When the separate severe-cadence boundary is breached, dispose of that recording attempt and automatically retry the local recording at most twice; this never repeats a paid model call. For Three.js only, if either participant remains severely choppy after all three real-time attempts, preserve the real-time cadence evidence and recapture both participants through the same deterministic frame-by-frame pipeline at the native 1200×676 resolution, exactly 30 fps for 12 seconds. Never change model code, lower resolution, insert synthetic frames, or call a model again during this fallback. Twigl still fails closed because the remote editor's animation clock cannot be safely virtualized.
- Record each participant at the policy's native 1200×676 viewport through the pinned Playwright recording pipeline configured to 30 fps and 8 Mbps instead of its upstream 25 fps / 1 Mbps defaults. Compose the only final output as a 1200×1352 vertical stack with A above B; do not generate the former side-by-side web version or pad the frame with empty black bands. The two-pixel adjustment from exact 16:9 keeps every yuv420p dimension even.
- Keep quality mode fixed by profile: every bundled Flash model uses explicit `max`; every other bundled model uses explicit `high`. The resolved plan and report must show the actual preset, and automatic fallback is forbidden.
- Give both participants the same generation lifecycle: 3600-second soft warning, 10800-second hard stop, 900-second output-idle stop, and 60-second progress interval. A timeout is infrastructure failure and includes the termination reason plus tool/file activity when available. Repairs reuse each participant's generation reasoning level, allow at most two rounds, and have a 3600-second hard limit per round.
- Bound browser-recording shutdown, finalize the exact interaction interval with FFmpeg, and validate duration, dimensions, and frame count before composition. A recorder shutdown or container-finalization problem is infrastructure failure, not model failure.
- Use two independent initial agent sessions (`codex exec` or `claude -p --session-id`) and separate workspaces. For a multi-round prompt, resume each participant's own session (`codex exec resume` / `claude -p --resume`) in its own workspace for every later creative round. Never expose the other model's files or logs in its prompt or writable roots. This is benchmark isolation, not hostile multi-tenant OS isolation.
- Isolate each runner from the user's personal configuration: Codex runs with `--ignore-user-config --ignore-rules --strict-config`; Claude Code runs with `--setting-sources project --strict-mcp-config --disable-slash-commands --no-chrome`, with `WebFetch`/`WebSearch` disallowed and provider/model environment variables reset from the profile. The workspace rules file is the only instruction source either runner should see.
- Send each later creative round as its exact normalized file content. Do not restate, interpret, or strengthen a vague follow-up such as `Make it better`; retaining and applying prior context is part of the test.
- Treat generated code as untrusted. Keep dependencies locked, prevent model-selected package installation, and execute only inside the run workspace.
- Keep provider credentials outside configuration, prompts, commands, workspaces, logs, and videos. Model profiles may name an environment variable or a native CLI login (`codex-login`, `claude-login`) only. Subscription logins work only inside their own CLI; a subscription can never be used through the other runner.
- Treat model timing and billing as different measurements. Model execution time is the measured local wall-clock interval for each runner process and excludes validation, recording, composition, and publishing. Token usage comes from `turn.completed` events (Codex) or the final `result` event's `modelUsage` (Claude Code), normalized to one schema where `input_tokens` counts every prompt token and `uncached_input_tokens = input_tokens - cached_input_tokens`. Do not infer an exact monetary charge from token counts or public list prices when the provider does not return a settled per-run amount; subscription plans cannot be truthfully allocated to one run.
- Complete all configured creative rounds before verification. Repair rounds are separate, reuse that participant's fixed generation reasoning (`max` for Flash, `high` otherwise), and repair only executable failures, with the same maximum rounds for both models. Do not count repair as a creative round, add unequal aesthetic coaching, or cherry-pick reruns.
- Let each native CLI perform its own documented transient retries, but do not wrap a paid phase in an additional automatic retry loop. A clean single-participant retry always requires a new described plan and explicit confirmation.
- A model that exhausts its repair budget receives a standardized failure panel in the comparison video. Abort without publishing on shared infrastructure failures.
- Encode and validate `comparison.mp4` as X-ready H.264 High/yuv420p within the configured X resolution, aspect-ratio, frame-rate, bitrate, duration, and file-size limits. Upload only this MP4; keep source, logs, individual recordings, and verification evidence local.
- Mix the pinned local `Brainiac` asset into every final MP4 as stereo AAC using the configured start offset, low background volume, and fades. Validate the audio stream and asset SHA-256. Mixkit permits the resulting social-media video use, but do not redistribute the raw MP3 in a Skill archive; recipients run `npm run fetch:bgm` to download their own local copy under the then-current license.
- Do not use CC Switch for the bundled DeepSeek V4.1 Flash / V4 Pro or GLM-5.3/GLM-5.3-Flash Coding Plan profiles. The `codex` profiles use each provider's official Responses endpoint; the `claude` profiles use each provider's official Anthropic-compatible endpoint.

## Setup boundary

The scripts require Node.js, npm, FFmpeg/FFprobe, Playwright, and at least one runner CLI: Codex CLI for `codex` profiles and Claude Code for `claude` profiles. Run `npm install` in this skill folder once. Run `npx playwright install chromium` if Playwright cannot find its browser. Run `npm run fetch:bgm` if the pinned local soundtrack asset is absent or fails its checksum. The publishing step remains optional until `SKILLFLOW_BENCHMARK_UPLOAD_URL` is configured.
